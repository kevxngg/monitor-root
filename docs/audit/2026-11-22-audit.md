## Decisions taken (2026-11-22, delegated by the owner)
1. **Retired signing key (S1).** Evidence from the published lineage (`apksigner lineage --print-certs -v` on build-104): the old signer already has **rollback = false**, so on Android 9+ a phone that installed any rotated build (2.9 / build 31 or later) refuses an update signed only with the old key. Decisions:
   - Lineage capabilities are **not changed**: removing installed-data/permission/auth would add no protection (Monitor defines no signature permissions and uses no shared uid) and could break the update path. The build now **fails if the old signer ever gets the rollback capability**.
   - `MIN_BUILD = 31`: builds from before the rotation are forced to update, which moves them onto the rotated lineage.
   - The updater requires the installed app's current key in the APK's lineage (`SignerCheck`), so silent installs cannot be done with the old key on rotated installs.
   - Git history is **not rewritten**: the files are already public (clones, forks, caches); a forced rewrite of `main` would not undo the leak and would break existing clones.
   - `minSdk` stays 26: Android 8 does not support rotation, so those phones trust only the old key whatever we do; raising minSdk would leave them without fixes, not protect them.
   - Residual risk: Android 8 phones, and phones still on a build before 2.9, would accept an APK signed with the old key if the user installs it by hand.
2. **CI.** The build job now compiles and tests without any key or write permission; signing runs in a separate job with only Android's tools, then publishes. Verified: signatures identical to build-104 and installed over 4.0 on a device.
3. **Repository settings.** Dependabot alerts, secret scanning and push protection enabled (0 open alerts).
4. **ROM helper (S4/S5)** stays documented as a risk of the ROM port; it does not affect the app as distributed.
